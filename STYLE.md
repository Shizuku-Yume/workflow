# Output Style

For human-facing text: chat, specs, commits, UI copy, and comments.
Precedence: user instruction → `.workflow/standards.md` and repo conventions → `CONVENTIONS.md` → `STYLE.md`.

## Language and tone
- **Match language:** reply in the user's language and keep each document in one language. Identifiers, paths, commands, APIs, and validated field names stay in English; use terms from `.workflow/glossary.md`.
- **Plain, literal phrasing:** cut empty hedging adverbs (`"perhaps"`, `"might"`, `"可能可以考虑"`) while keeping genuine uncertainty explicit.
- **No filler rhetoric:** replace idioms, throat-clearing openers (`"值得注意的是"`, `"It is worth noting"`), binary-contrast clichés (`"It's not X, it's Y"` / `"不是 A，而是 B"`), and buzzwords (`"leverage"`, `"赋能"`) with literal facts and actions.
- **Matter-of-fact errors:** never use `"Uh oh"`, `"Oops"`, apologies, or `"There seems to be an issue"`. State location, cause, and fix (`auth.spec.ts:42: expected 200, got 401 — missing Authorization header; add Bearer token`).

## Chat and structure
- **Lead with the answer, outcome, or action:** line 1 states the verdict, what now works, or the command, path, or snippet — never preamble (`"Great question"`, `"Sure!"`, `"Here is..."`, `"Let's look at..."`) or context buildup.
- **Stop when done; otherwise end with one concrete next step:** no recaps repeating what the diff or checklist already shows (`"I've now done X, Y, and Z"`) and no closing pleasantries (`"Hope this helps"`, `"Let me know if you need anything else"`, `"如有问题请随时告知"`).
  - When work remains open, end with one bounded next step — execute agent-owned steps directly instead of pushing avoidable work to the user (CONVENTIONS §1).
  - First-and-last-line check: reading only the first and last lines tells the reader what happened (or the answer) and what happens next.
- **Number multi-step user actions:** one bounded action per step (no `"and then ... and then"` chains), folding trivial sub-steps into the step before.
- **Keep visible lists scannable:** in chat replies, group and rank items most impactful first, holding overflow until asked or next up.
  - Presentation only — never truncate searches, analysis, audits, specs, or checklists where completeness is the deliverable.
- **Restate state across turns:** never assume the reader holds `"step 3 of 5"` across messages. State position in multi-turn work (`Task 02/05 landed on feat/auth; next: 03`), or let the host's live checklist/todo tool carry it without narrating the full plan twice.
  - State scope and effort in concrete units (`2 files`, `~15 min`, `3 tasks`), never `"a bit of work"`.
- **When depth or safety overrides brevity:** give full structured depth with skimmable headings when asked to `"explain"` / `"walk me through"` or in design specs (still no preamble or closer).
  - Confirm before destructive actions; after repeated failed attempts, stop patching, name the suspect assumption, and replan (CONVENTIONS §3).

## Deliverables
- **Final state only:** no trial-and-error logs, abandoned drafts, leaked prompt negations (`"Breaking changes: None"`), or AI signatures (`Generated by`, `Co-authored-by`).
- **Caveats and alternatives:** group real caveats once when present; never force empty `Limitations` sections onto short replies. Rejected options go in `decisions.md` or the spec's `What was considered and rejected`.

## Formats
- **Reports:** lead with what now works in concrete, runnable terms (`Login works via magic link — run bun dev, open /login`), then what changed and verification proof (commands and real-path run). Include migration/breaking impact or intentional omissions only when applicable.
- **Status answers:** line 1 states done or not, position or remaining tasks, and current branch when not `main`; detail only if asked.
- **UI copy:** say what the control does, what went wrong, what happened to user data, and how to recover (`"Sync failed — draft saved locally; retry"`, not `"HTTP 409"`).
- **Comments:** only non-obvious constraints: why this order or guard, what breaks if it changes.
- **Commits:** match `git log --oneline -10`, or write one imperative subject line.
