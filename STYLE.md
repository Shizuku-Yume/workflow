# Output Style

Applies to everything a person reads: chat, specs, commit messages, UI text, and code
comments. Ranks last in precedence behind the user's instruction, `.workflow/standards.md`,
repo conventions, and `CONVENTIONS.md`.

## Language and terms
Write in the user's language and keep each document in one language. Keep code,
identifiers, commands, paths, and structured field names (such as `decisions.md` headers)
in their original/English form. Use `.workflow/glossary.md` terms consistently; define a
new technical term where it first appears.

## Clean deliverables (no defense or generation traces)
- **Final state only:** Present code, comments, docstrings, commits, PRs, specs, and
  summaries as if written right the first time — no trial-and-error, intermediate errors,
  abandoned drafts, or unstructured "why we didn't do X" (`Instead of` belongs only in
  `decisions.md` and spec rejected-options sections).
- **No leaked instructions:** "Do not mention X" means X is absent, never "we do not
  address X".
- **Launch, not defense transcript:** State plainly what holds. Collect real caveats in
  one `Limitations` or `Known Issues` section rather than sprinkling disclaimers into
  every paragraph. State trade-offs and unfavorable numbers plainly without apologizing.
- **No AI markers:** Never add `Generated by` / `Co-authored-by` AI signatures, `"here
  is..."` openers, or model-voice transitions (`"it is worth noting"`, `"in summary"`,
  `"firstly... secondly..."`, `"值得注意的是"`, `"综上所述"`).

## Chat and reporting
Lead with the answer and stop when complete. Match length to the question: one line for
yes/no, full detail for design.
- **Work report:** what changed, how it was verified, what was left out (and when it matters).
- **Status answer:** done or not and what tasks remain in the first sentence, plus the
  branch read if not main; detail only if asked.

## Front-end text
Write for the person using the page, not the implementer:
- Say what the control is and what happens when pressed, in user vocabulary (`"Sync failed"`, not `"HTTP 409 from upstream"`).
- On error, state what happened to their data and what they can do next.

## Code comments and commits
- **Comments:** explain only what code cannot show — why this order, why this guard, what breaks if changed.
- **Commits:** match `git log --oneline -10`; if no convention exists, write one imperative subject line stating what changed and why, with details in the body.
